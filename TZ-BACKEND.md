## 1. Архитектура

Своего сервера нет и не появляется. Всё на Supabase:

```
Сайт (index.html)              Панель (admin.html)           Кабинет (cabinet.html)
  cms.js  track.js  app.js       js/admin/api.js               js/auth.js
     │       │        │               │                            │
     │ RPC   │ RPC    │ Auth          │ таблицы + RPC + Realtime   │ Auth + RPC
     ▼       ▼        ▼               ▼                            ▼
┌──────────────────────────── Supabase ────────────────────────────────────┐
│ Postgres: таблицы, RLS, триггеры, RPC  ← единственное место с правилами  │
│ Auth (email, Google, Mail.ru-мост)   Storage (bucket media)   Realtime   │
│ Edge Functions: mailru-auth                              pg_cron [новое] │
└──────────────────────────────────────────────────────────────────────────┘
```

Принципы:

1. **Правила живут в базе.** Интерфейс только подсказывает; всё, что влияет на деньги и
   права, проверяет Postgres (RLS, триггеры, RPC). Сейчас часть правил есть только в
   `js/admin/views/leads.js` — это главный разрыв (см. §7).
2. **Посетитель не пишет в таблицы.** Только через `submit_lead`, `track`, `check_coupon`,
   `public_site`.
3. **Одно определение — одна формула.** Каждая метрика считается в одном месте (SQL) и
   описана в §5. Панель не пересчитывает её по-своему.
4. **Демо-режим (`?demo`) обязан вести себя так же**, как живая база: те же правила, те же
   формулы.

## 4. Процессы

### 4.1. Посещение → события **[сделано, этап 2; этап 7 добавил номер обращения]**

   `ref` только у `wa_click` и только вида «5 знаков алфавита без 0, O, 1, I, L».

### 4.3. Работа с заявкой **[снято этапом 7 — действует §4.11]**

> В панели нет канбана и статусов «новая / на связи / предложение»: в журнал попадают только
> продажи (`won`) и возвраты (`lost`). Сторож `leads_guard` и история в базе остаются как
> есть — на них держатся правила продажи из §4.4.

Статусы и переходы:

```
new ──► contacted ──► quoted ──► won
 │          │            │        │
 └──────────┴────────────┴──► lost ◄┘ (переоткрытие / возврат)
 └──► spam
```

Любой переход разрешён (менеджер может вернуть заявку назад), но сервер при каждом:

| Событие | Что делает база |
|---|---|
| уход из `new` или первая запись звонка / WhatsApp / заметки | ставит `first_response_at`, один раз |
| вход в `won`, `lost`, `spam` | ставит `closed_at`: присланную дату, если она не в будущем, иначе `now()` |
| выход из закрытого статуса | очищает `closed_at` |
| смена статуса, ответственного | пишет в историю, кто и что |
| вход в `lost` | требует `lost_reason` |
| заявка создана вручную (`phone`, `walk_in`, `instagram`, `manual`) | ставит `first_response_at = created_at`, статус не ниже `contacted` |

Сейчас последние две строки и «присланная дата» делает только интерфейс; дату продажи он
ставит вторым запросом поверх триггера. Перенести в триггер `BEFORE INSERT OR UPDATE`.

### 4.4. Продажа **[сделано, этап 1; форма — этап 7]**

Сайт не принимает оплату; продажу вносит менеджер. Правила, которые обязана держать база:

1. `status = 'won'` ⇒ `value > 0`.
2. `profit` пустой или `0 ≤ profit ≤ value`.
3. `closed_at` (дата продажи) не в будущем.
4. `currency` = валюта из «Контакты и реквизиты», ставит сервер.
5. Любое изменение `value`, `profit`, `closed_at` у закрытой заявки пишется в историю:
   кто, было → стало (новый вид записи `money`).
6. Удаление заявки (только владелец) попадает в `audit_log`.

Сейчас ни одно из правил 1–5 база не проверяет. Проверено: запросом в обход панели
создаётся продажа без суммы, с доходом 5000 и датой через месяц; правка суммы уже
закрытой продажи не оставляет следа.

Реализация: триггер-сторож на `leads`. Проверки срабатывают, когда меняется статус или
денежные поля, — старые продажи без суммы не блокируются и остаются в срезе «Продажи без
дохода агентства».

**Возврат / отмена после продажи** (решено): менеджер переводит продажу в «Отказ» с
причиной «Возврат». Продажа уходит из выручки того дня, которым была записана, промокод
освобождается, в истории остаётся запись, кто и когда вернул. Сумма и доход в строке
сохраняются (для справки), в отчёты не попадают. «Возврат» добавить в список причин отказа.

### 4.9. Аккаунт клиента и кабинет **[сделано, этап 4; «Мои заявки» сняты этапом 7]**

- Регистрация → триггер создаёт `profiles` (роль `client`, согласие только явное).
- **Подтверждение почты [новое].** Вход через Google и Mail.ru подтверждения не требует —

  дату не отдаёт. В тексте политики конфиденциальности на сайте дописать, зачем собирается
  дата рождения.
- Согласие на рассылку: дата и источник хранятся; выгрузка — `audience_list()`.
- **Разрыв:** кабинет читает таблицу `bookings` и обещает «отправьте заявку — она появится

### 4.11. Всё через WhatsApp **[сделано, этап 7 — заменяет §4.2, §4.3 и часть §4.9]**

Заказчик работает только в WhatsApp, поэтому сайт не собирает заявки, а помогает клиенту
начать разговор.

**Сайт**

- Формы «имя, телефон, сообщение» нет. Вместо неё в блоке контактов — кнопки WhatsApp и
  «позвонить».
- Каждая ссылка на WhatsApp открывает чат с готовым коротким текстом о том, на что нажал
  человек, **на текущем языке сайта**; при переключении языка тексты пересобираются:

  | Откуда нажали | RU | EN | HY |

  | карточка или описание тура | Здравствуйте! Хочу спросить про тур «Шарм-эль-Шейх». | Hello! I'd like to ask about the Sharm El Sheikh tour. | Բարև ձեզ։ Հետաքրքրում է «Շարմ էլ Շեյխ» տուրը։ |

- Карточка тура: нажатие открывает описание, как сейчас; главная кнопка в описании —
  «Написать про {тур}». На самой карточке — зелёная кнопка WhatsApp, которая пишет сразу.
- В конец сообщения добавляется короткий номер обращения: «№ K7M2». Он связывает
  разговор в WhatsApp с тем, что знает сайт: рекламная метка, тур, язык, устройство,
  промокод. Номер — производная от `sid` визита (5 знаков без похожих символов), отдельно
  нигде не хранится; уходит в событии `wa_click`.

**База**

- `events`: у `wa_click` появляются поля `ref` (номер обращения) и уже существующие
  `tour`, `label` (где нажали), `utm_*`.
- RPC `wa_ref(code)` — для владельца и менеджера: последнее за 90 дней событие `wa_click`

- `submit_lead` у гостей отзывается (`revoke … from anon`): формы нет, значит и атаковать
  нечего. Функция и лимиты остаются в базе на случай возврата формы.
- Письмо о заявке (`lead-mail`, вебхук, повтор по расписанию) выключается: заявок с сайта
  нет. Код остаётся в репозитории, расписание и вебхук не создаются.
- Продажа с номером обращения получает `utm_*`, `tour`, `lang`, `device` из `wa_ref`;
  без номера — источник выбирает владелец (WhatsApp, звонок, визит, Instagram).

**Панель**

- «Заявки» → **«Продажи»**: таблица продаж и возвратов. Канбан и статусы «новая / на
  связи / предложение» из интерфейса убираются (в базе остаются). Кнопка одна —
  «Продажа»; в её форме первое поле — «Номер обращения (если клиент писал с сайта)»,
  по нему подставляются тур и источник.
- Сводка: воронка **посещения → клики в WhatsApp и по телефону → продажи**. Убираются:
  первый ответ, «требуют внимания», прогноз по предложениям, живые уведомления о заявках.
  Причины отказов остаются только как причины возвратов.
- Интерес к турам: открытия описания → клики в WhatsApp по туру → продажи по туру.
- Кампании и каналы: продажи и доход — по номеру обращения; «заявки» в таблицах
  заменяются на «обращения в WhatsApp» (клики).
- «Готовность сайта»: пункты про заявки и письма убираются.

**Кабинет клиента**: блок «Мои заявки» убирается, остаётся профиль. `my_requests()` в
базе остаётся, сайт её не вызывает.

**Словарь метрик**: см. §5 — он переписан под эту схему.

**Как сделано** (миграция `070_whatsapp.sql`, тест `70-whatsapp.test.mjs`):

- *Тексты* — `js/wa.js` (чистые функции, проверяются тестом слово в слово по таблице выше).
  Ссылку помечает атрибут: `data-wa="tour"` + `data-wa-tour`, `data-wa="service"` +
  `data-wa-topic`, `data-wa="promo"` + `data-wa-coupon`; без атрибута — общий текст.
  `js/app.js` пересобирает все ссылки при смене языка, приходе туров и контактов из панели и
  когда посетитель взял промокод. «Подбор тура» шлёт свой подробный текст, чек-лист —
  «Хочу спросить про: документы для поездки»; номер обращения дописывается и к ним.
- *Номер обращения* — FNV-1a от `sid`, 5 знаков алфавита `23456789ABCDEFGHJKMNPQRSTUVWXYZ`
  (`js/track.js`, зеркало в `js/admin/metrics.js`). В сообщении — последней строкой:
  `№ K7M2X`, одинаково на всех языках, чтобы владелец искал глазами один знак.
- *Ввод номера* — `ref_norm()`: регистр, «№», пробелы и русская раскладка не мешают.
- *`wa_ref(code)`* — время, место, метки, язык и устройство последнего клика; тур и промокод —
  из последнего клика, где они были (человек мог нажать «про Дубай», а потом общую кнопку).
- *Продажа с номером* — колонка `leads.ref` и триггер `leads_attribution`: подставляет
  `utm_*`, домен перехода, язык, устройство; тур и промокод — если не вписаны руками;
  источник становится WhatsApp. Номер не найден за 90 дней → ошибка `ref_not_found`, продажа
  вносится без номера. Пока номер не меняют, записанные метки не трогаются.
- *Канал продажи* (`lead_channel`) — с номером: метка → домен перехода → прямой заход;
  без номера: источник, выбранный владельцем.
- *Даты* — продажи канала, кампании и тура считаются по дате продажи, как и у владельца:
  после этапа 7 выручка в панели одна, «по заявкам периода» больше нет.
- *Возврат* — запись журнала в `lost` с причиной (список в панели: «Возврат», «Клиент
  передумал», «Отказ в визе», «Отмена рейса или отеля», «Перенос поездки», «Другое»).
- *Демо* — `?cms=demo` ничего не шлёт в базу: клик остаётся в `localStorage` браузера,
  и демо-панель находит его по номеру.

### 4.12. Напоминания о вылетах **[сделано, этап 9]**

**Почему не полностью автоматически.** Программа может сама написать клиенту в WhatsApp
только через официальный доступ Meta: проверка компании и плата за каждое сообщение.
Заказчик платить за это не хочет. «Свой код», который рассылает через обычный WhatsApp
(управление WhatsApp Web с сервера), нарушает правила WhatsApp и приводит к блокировке
номера, а ещё требует отдельного постоянно работающего сервера — он стоит дороже, чем
официальные сообщения. Поэтому: система готовит всё сама, а последнее нажатие «отправить»
делает человек со своего телефона.

**Как это работает.**

1. Владелец в форме продажи заполняет дату вылета, дату возвращения и язык клиента
   (EN / RU / HY; подставляется из номера обращения, если он есть).
2. Каждый день в 11:00 по Еревану система собирает, кому писать сегодня: вылет завтра →
   «хорошего полёта»; вернулись вчера → «с возвращением».
3. Владельцу на почту агентства уходит одно письмо «Сегодня написать: 3 клиента» — в нём
   по каждому имя, направление и кнопка **«Отправить в WhatsApp»**. Кнопка открывает чат с
   этим клиентом, текст уже набран на его языке; остаётся нажать «отправить».
   Если писать некому — письмо не уходит.
4. То же самое — в панели, блок «Написать сегодня» на сводке, со счётчиком в меню.
   После нажатия кнопки запись отмечается «отправлено»; можно отметить и вручную.

**Тексты** (правятся в панели, «Шаблоны ответов», по одному на язык):

- накануне вылета: «Здравствуйте, Мариам! Завтра ваш вылет в Шарм-эль-Шейх. Желаем
  хорошего полёта и отличного отдыха! SAM TRAVEL»;
- после возвращения: «С возвращением, Мариам! Надеемся, Шарм-эль-Шейх понравился. Будем
  рады вашему отзыву» (+ ссылка, если задана в настройках).

Подставляются только имя (первое слово) и название направления на языке клиента.

**Правила.**

- В список попадает продажа, если она не возвращена, у неё есть телефон и нужная дата.
- Перенос даты переносит напоминание; возврат продажи его снимает.
- Продажа внесена после 11:00 накануне вылета → клиент сразу появляется в блоке
  «Написать сегодня» в панели (письмо за этот день уже ушло).
- Неотправленное вчера не пропадает: висит в блоке с пометкой «просрочено», пока дата
  вылета не пройдёт.
- Выходные: письмо уходит и в выходной — клиенту сообщение нужно именно накануне.

**База.** `leads`: `depart_on date`, `return_on date`; язык — существующее `lang`.
Таблица `wa_reminders` (продажа, вид `bon_voyage` | `welcome_back`, на какой день, статус
`due` | `sent` | `skipped`, кто и когда отметил). Триггер на `leads` создаёт, переносит и
снимает записи. RPC `reminders_today()` для панели и `reminder_done(id)`. Письмо шлёт
существующий механизм писем (`notify_log`, Edge Function почты) по расписанию `pg_cron`
в 11:00 по Еревану; час и ссылка для отзыва — в `site_settings.whatsapp`.

**Панель.** Поля в форме продажи; столбец и фильтр «Вылет» в «Продажах»; блок «Написать
сегодня» и блок «Ближайшие вылеты» (7 дней) на сводке; настройки в «Контакты и
реквизиты»: напоминания включены, час письма, ссылка для отзыва.

**Места под автоматическую отправку — закладываются сейчас, включаются после разрешения
Meta.** Чтобы потом ничего не переделывать, этап 9 сразу делает:

- поле `leads.wa_opt_in` и галочку в форме продажи «Клиент согласен получать сообщения
  в WhatsApp» — согласие копится уже сейчас, без него автоотправка запрещена правилами
  WhatsApp;
- у напоминания статус `auto_sent` и поля «попытки», «ответ сервиса», «когда отправлено
  системой» — сейчас не используются;
- настройку `site_settings.whatsapp.mode`: `remind` (сейчас, единственный рабочий режим)
  или `auto`; в «Контакты и реквизиты» переключатель «Отправлять автоматически» виден, но
  выключен с подписью «Станет доступно после подключения WhatsApp Business Platform»;
- одну точку в коде, через которую уходит сообщение: функция `send_reminder(id)`. Сейчас
  она ничего не отправляет и оставляет запись человеку. При подключении в неё добавляется
  вызов WhatsApp Cloud API — и больше нигде ничего не меняется;
- файл `supabase/templates/whatsapp.md` с текстами двух шаблонов на трёх языках в формате
  для подачи в Meta ({{1}} имя, {{2}} направление).

**Что останется сделать, когда придёт разрешение:** внести токен и ID номера в секреты,
подать шаблоны на одобрение, дописать вызов API в `send_reminder`, включить переключатель.
В режиме `auto` письмо владельцу продолжает приходить, но только по тем, кому система
отправить не смогла (нет согласия, ошибка доставки). Цена — порядка 0,03 $ за сообщение,
абонентской платы нет.

**Как сделано** (миграция `090_reminders.sql`, тест `90-reminders.test.mjs`):

- *Список и текст собирает база* — `reminders_list(день)`: одно определение для панели
  (`reminders_today()`) и для письма (`reminders_digest()`). В ответе по каждому клиенту —
  готовый текст на его языке и ссылка `wa.me/<номер>?text=…`.
- *Когда запись в списке* — «хорошего полёта»: с кануна вылета по день вылета включительно;
  «с возвращением»: со следующего дня после возвращения и ещё 7 дней. Всё, что должно было
  уйти раньше сегодняшнего дня, помечено «просрочено».
- *Кому положено* — продажа не возвращена, в телефоне не меньше 8 цифр, дата задана. Возврат
  или стёртая дата снимают неотправленное (`skipped`), отмена возврата возвращает.
- *Перенос даты* — та же запись переезжает на новый день. Уже отправленное снова становится
  «написать», если новый день ещё не прошёл.
- *Язык* — `leads.lang`; не из трёх — русский. У продажи с номером обращения язык ставит
  триггер этапа 7 (язык визита), поменять можно в карточке.
- *Тексты* — `wa_templates.kind` (`bon_voyage` | `welcome_back`), один на язык. Подстановки
  `{name}`, `{tour}`, `{review}`; кусок в [квадратных скобках] выпадает целиком, если
  подставить нечего (нет направления, не задана ссылка для отзыва). Шаблон удалён или пуст —
  берётся текст по умолчанию.
- *Отметка* — `reminder_done(id)` ставит «отправлено», пишет в историю продажи, кто и что
  отправил; `reminder_done(id, false)` снимает отметку. Кнопка в письме запись не отмечает.
- *Письмо* — `reminders_tick()` раз в 5 минут: в час из настроек кладёт в `notify_log` одну
  строку на день (`kind = 'reminders'`, список заморожен в `payload`) и подталкивает функцию
  `lead-mail`; та же функция повторяет неудачные. Пустой день — строки нет.
- *Настройки* — `site_settings.whatsapp`: `enabled`, `mail_hour` (0–23), `review_url`,
  `mode`. Проверяет триггер: режим `auto` отклоняется, пока не подключена WhatsApp Business
  Platform. На публичный сайт ключ не уходит.
- *Демо* — те же правила в `js/admin/reminders.js`; несколько свежих продаж каждый день
  передатируются, чтобы на сводке было кому написать.

|---|---|---|---|
| Посещение | событие `page_view` (= одна загрузка страницы) | `events.ts` | трафик, сводка |
| Обращение | `wa_click` + `tel_click` | `events.ts` | везде, где раньше были «заявки» |
| Продажа | запись журнала в `won` с `value > 0` | `closed_at` | сводка, каналы, кампании, туры |
| Продажа с сайта | продажа с номером обращения (`ref`) | `closed_at` | трафик, кампании |
| Возврат | запись журнала в `lost` | `closed_at` | сводка |
| Выручка | Σ `value` продаж | `closed_at` | сводка, каналы, кампании |
| Доход агентства | Σ `profit`; где пусто — `value × маржа`, с пометкой ≈ | `closed_at` | сводка, ROMI |
| Средний чек | выручка ÷ число продаж | `closed_at` | сводка |
| Конверсия в продажу | продажи ÷ обращения за период | `closed_at` / `ts` | сводка |
| Посещения → обращение | обращения ÷ посещения | `ts` | сводка, трафик, кампании |
| Канал | с номером обращения: `utm_source` → домен перехода → прямой заход; без номера: выбранный источник | — | сводка, трафик |
| Выручка канала / кампании | Σ `value` продаж с номером обращения этого канала / кампании | `closed_at` | трафик, кампании |
| Интерес к туру | `tour_open` → `wa_click` с этим туром → продажи с этим туром | `ts` / `closed_at` | сводка, трафик |
| Цена обращения / продажи | расход ÷ обращения / продажи кампании | вся жизнь кампании | кампании |
| ROMI | (доход − расход) ÷ расход | вся жизнь кампании | кампании |
| CTR промо | клики ÷ показы | `events.ts` | промо |

Исключены этапом 7: «Заявка», «Первый ответ», «В норматив», «Прогноз», выручка «по заявкам
периода», конверсия «продажи ÷ (продажи + отказы)».

Что закреплено:

1. **Выручка одна — по дате продажи.** И у владельца, и у маркетолога.
2. **Канал определяет одна SQL-функция** `lead_channel()` (для событий — `channel_of()`);
   её используют сводка, трафик и кампании.
3. **Конверсия в продажу может быть больше 100 %**: обращение — это нажатие на сайте, а
   продажа могла начаться со звонка или визита. Поэтому рядом показано, сколько продаж —
   с номером обращения.
4. **Рабочие часы** (`work_minutes`, `site_hours`) остаются в базе, отчёты их не используют.
5. **Валюта одна** (`company.currency`). Цена «от» в карточке тура — отдельное поле для
   сайта, в отчётах не участвует.

## 6. Контракт API

Сайт:

| Вызов | Статус | Что делает |
|---|---|---|
| `public_site()` | есть | весь контент одним ответом |
| `track(events)` | есть | события с лимитами; у `wa_click` — номер обращения `ref` |
| `submit_lead(p)` | в запасе | у гостей отозвана; сайт не вызывает |
| `check_coupon(code)`, `my_requests()` | в запасе | остаются в базе; сайт не вызывает |
| `my_profile()`, `finish_onboarding()`, `set_birth_date()` | есть | кабинет клиента — профиль |

Панель:

| Вызов | Статус | Что делает |
|---|---|---|
| `whoami()` | есть | роль и имя |
| таблица `leads` (чтение, вставка, правка) | есть | журнал продаж и возвратов; правила §4.4 и подстановка по номеру обращения — в триггерах; чтение страницами по `closed_at` |
| `wa_ref(code)` | есть | что сайт знает о визите с таким номером — владельцу и менеджеру |
| `reminders_today()` | есть | кому написать сегодня (текст и ссылка `wa.me`) и вылеты на 7 дней — владельцу и менеджеру |
| `reminder_done(id, done)` | есть | отметить напоминание отправленным или снять отметку |
| `stats_sales(from, to)` | есть | `kpi`, `daily`, `managers`, `refund_reasons`, `channels`, `tours`, `contact_heat` — всё из §5 |
| `stats_traffic(from, to)` | есть | `daily`, `sources`, `campaigns`, `tours`, `funnel`, `heat`, `contact_heat`, `promos`, устройства, языки, блоки; чтение свёртки |
| `stats_coupons()` | есть | записи журнала и продажи по коду, без PII |
| `birthdays(month)` | есть | именинники месяца: имя, почта, дата, язык — владельцу и маркетологу |
| `users_list()`, `audience_list()` | есть | клиенты и подписчики |
| `set_role(user, role)` | есть | защита последнего владельца |
| `notify_status()` | в запасе | письма о заявках; панель не вызывает |
| контентные таблицы, `site_settings`, `audit_log`, Storage `media` | есть | |

Realtime по `leads` панель больше не слушает: живых уведомлений о заявках нет.

**Почему нужен `stats_sales`** (история, этап 3). Раньше сводка скачивала заявки в браузер и считает сама.
Запрос просит 3000 строк, но Supabase по умолчанию отдаёт не больше 1000 за запрос
(API → Max rows). После тысячной заявки выручка, конверсия и рейтинг менеджеров начнут
молча терять старые записи. Целевое состояние: цифры считает SQL, а список заявок
грузится так: все открытые + закрытые за выбранный период, остальное — по поиску и
страницами.

## 8. Эксплуатация

| Тема | Требование |
|---|---|
| Миграции | Вместо двух файлов «вставить в SQL Editor» — папка `supabase/migrations/` с номерами, накат через Supabase CLI. Изменения из §7 — отдельными миграциями, повторный запуск безопасен |
| Стенд | Второй проект Supabase для проверки миграций; боевой ключ в `supabase-config.js` не меняется |
| Регион | Проект в Сиднее (~300 мс до Армении). Переезд во Франкфурт — по плану §8.1 |
| Резервные копии | На бесплатном тарифе их нет. Либо тариф Pro (ежедневные копии), либо еженедельный `pg_dump` по расписанию в приватное хранилище |
| Вход в панель | Почта и пароль, минимальная длина пароля 10. Двухфакторного входа нет (решение заказчика); готовая реализация лежит в истории, коммит `cf7067b` |
| Секреты | `service_role`, ключи Mail.ru и почтового сервиса — только в секретах Edge Functions |
| Наблюдение | «Готовность сайта» показывает: версию схемы, время последнего события, последней заявки |
| Скорость | `public_site()` ≤ 300 мс, `stats_*` за 90 дней ≤ 1 с при 10 000 заявок и 1 млн событий. Индексы: `leads(closed_at)`, `leads(assigned_to)`, `leads(user_id)`, `events(utm_campaign, ts)` |
| Нагрузка | До 100 заявок в день ≈ 36 000 в год, события — миллионы строк в год. Поэтому расчёт цифр в SQL (`stats_sales`), загрузка заявок страницами и свёртка событий — обязательные пункты, а не «на вырост». Общий лимит `submit_lead` поднять с 40 до 60 заявок за 10 минут |
| Демо | `DemoApi` реализует те же правила §4 и формулы §5; расхождение = ошибка |

### 8.1. Переезд: куда и как

**Куда.** Остаёмся на Supabase, меняем только регион: новый проект во Франкфурте
(`eu-central-1`). Регион у существующего проекта поменять нельзя, поэтому это новый проект
и перенос. Уходить с Supabase на свой сервер не нужно: вход, права по строкам, функции,
хранилище фото и живые уведомления — это весь наш бэкенд, и на другой платформе его
пришлось бы писать заново (отдельный API, авторизация, хостинг, обновления), не получив
ничего взамен. SQL при этом обычный Postgres — если когда-нибудь понадобится, базу можно
унести целиком.

**Когда.** Первым шагом, до работ из §7. Старую базу решено не переносить, поэтому шаги
2–3 сводятся к запуску миграций на чистом проекте; контент и фото менеджер вносит через
панель уже в новый проект.

**Порядок.**

1. *Новый проект.* Supabase → New project → Frankfurt. Записать URL, publishable key,
   пароль базы.
2. *Схема и данные* — через Supabase CLI, тремя файлами со старого проекта:
   `supabase db dump --role-only`, `supabase db dump` (схема), `supabase db dump --data-only
   --use-copy` → накатить `psql` на новый. В выгрузку входят `auth.users` с хешами
   паролей: аккаунты и пароли сохраняются, людям нужно только войти заново.
   Если в старой базе нет ничего ценного (только тестовые заявки и свой аккаунт) — проще:
   выполнить `schema.sql` + `admin.sql` на новом проекте, зарегистрироваться и назначить
   владельца, как в `SETUP-ADMIN.md`.
3. *Фото.* Файлы бакета `media` выгрузка не переносит: скопировать скриптом (скачать из
   старого, загрузить в новый с теми же путями), затем заменить адрес старого проекта в
   `tours.photo_url`, `reviews.photo_url`, `team.photo_url` одним `update`.
4. *Вход.* Authentication → URL Configuration: Site URL и Redirect URLs как в старом.
   Google: в Google Cloud добавить новый адрес
   `https://<новый-ref>.supabase.co/auth/v1/callback`, ключи вставить в новый проект.
   Mail.ru: в приложении Mail.ru поменять Redirect URI на новый адрес функции.
   Шаблоны писем и SMTP — перенести руками.
5. *Функции.* `supabase functions deploy mailru-auth` в новый проект; `lead-notify` не
   переносится, папка удаляется из репозитория; вместо неё — `lead-mail`. Секреты завести заново (
   `MAILRU_*`, `SB_URL`, `SB_SERVICE_ROLE_KEY`, `SITE_URL`). Database Webhook на вставку
   в `leads` создать заново.
6. *Сайт.* Единственное место в коде — `js/supabase-config.js` (URL и ключ). CSP в
   страницах разрешает `*.supabase.co`, её менять не нужно. Поднять номер версии в
   ссылках на скрипты, чтобы браузеры не держали старый конфиг. Обновить `SETUP-AUTH.md`.
7. *Проверка на новом проекте до переключения:* `rls.test.mjs`, вход по почте, Google и
   Mail.ru, заявка с формы → панель, загрузка фото, сценарий из §9.
8. *Переключение.* Вечером: шаг 2 повторить начисто (свежие данные) → `git push` с новым
   конфигом → проверить заявку на боевом домене. Заявки, отправленные в эти минуты, не
   теряются: форма при недоступной базе открывает WhatsApp.
9. *После.* Старый проект поставить на паузу, удалить через две недели. Ключи старого
   проекта нигде не остаются.

**Тариф.** На бесплатном нет резервных копий, а проект без обращений неделю засыпает.
Для боевой базы с клиентами — Pro (25 $/мес., ежедневные копии). Если пока бесплатный —
еженедельный `supabase db dump` по расписанию в приватное хранилище.

## 9. Приёмка

Бэкенд принят, когда:

1. Все проверки `rls.test.mjs` зелёные, включая новые: менеджер не меняет роли; продажа
   без суммы, с доходом больше суммы и с датой в будущем отклоняется; промокод считается
   при любой форме продажи; клиент видит свои заявки и не видит чужих; маркетолог не
   получает телефоны ни одним вызовом; 201-е событие одного `sid` отбрасывается.
2. Сквозной сценарий на стенде: заход по UTM-ссылке → заявка с промокодом →
   панель → «На связи» → «Предложение» → «Продажа» вчерашней датой. После этого:
   выручка и доход появились во вчерашнем дне сводки; у кампании +1 заявка, +1 продажа,
   ROMI пересчитан; у промокода «использован 1»; в истории заявки видно, кто и когда;
   у менеджера +1 продажа; в кабинете клиента статус «оформлено».
3. Те же цифры в сводке, в CSV-выгрузке заявок и в прямом SQL-запросе совпадают.
4. При 1500 заявках в базе сводка за «всё время» сходится с SQL.
5. Переоткрытие продажи убирает её из выручки, возвращает промокод и оставляет запись в
   истории.

## 10. Что нужно от заказчика

Открытых вопросов по устройству бэкенда нет. Для работ нужны доступы — все аккаунты на
имя заказчика:

1. Аккаунт Supabase с привязанной картой (тариф Pro) — создаём в нём проект во Франкфурте.
2. Доступ к DNS домена `samtravel.am` — подтвердить домен в почтовом сервисе, чтобы письма
   подтверждения и письма о заявках не попадали в спам.
3. Google Cloud (вход через Google) и приложение Mail.ru (вход через Mail.ru) — прописать
   новые адреса возврата.
4. Адрес почты, на который слать письма о заявках (по умолчанию — почта из «Контактов»).
5. Текст для политики конфиденциальности: зачем собирается дата рождения.

Принято по умолчанию, меняется без переделок: возраст при регистрации от 16 лет; валюта
панели USD; почтовый сервис выбираем мы (с бесплатным уровнем); проверочный стенд —
отдельный бесплатный проект Supabase.
