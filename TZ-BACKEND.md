# SAM TRAVEL — ТЗ на бэкенд

Версия 6 · 6 октября 2026 · статус: решения собраны, ждёт подтверждения

Документ описывает, как должен работать бэкенд, чтобы панель (`admin.html`) показывала
верные цифры: какие данные где рождаются, кто их меняет, по каким правилам считаются
метрики и что нужно доделать в текущей базе.

Пометки: **[есть]** — уже работает, **[доработать]** — есть, но с ошибкой или дырой,
**[новое]** — нужно написать.

## 1. Архитектура

Своего сервера нет и не появляется. Всё на Supabase:

```
Сайт (index.html)              Панель (admin.html)           Кабинет (cabinet.html)
  cms.js  track.js  app.js       js/admin/api.js               js/auth.js
     │       │        │               │                            │
     │ RPC   │ RPC    │ Auth          │ таблицы + RPC + Realtime   │ Auth + RPC
     ▼       ▼        ▼               ▼                            ▼
┌──────────────────────────── Supabase ────────────────────────────────────┐
│ Postgres: таблицы, RLS, триггеры, RPC  ← единственное место с правилами  │
│ Auth (email, Google, Mail.ru-мост)   Storage (bucket media)   Realtime   │
│ Edge Functions: mailru-auth                              pg_cron [новое] │
└──────────────────────────────────────────────────────────────────────────┘
```

Принципы:

1. **Правила живут в базе.** Интерфейс только подсказывает; всё, что влияет на деньги и
   права, проверяет Postgres (RLS, триггеры, RPC). Сейчас часть правил есть только в
   `js/admin/views/leads.js` — это главный разрыв (см. §7).
2. **Посетитель не пишет в таблицы.** Только через `submit_lead`, `track`, `check_coupon`,
   `public_site`.
3. **Одно определение — одна формула.** Каждая метрика считается в одном месте (SQL) и
   описана в §5. Панель не пересчитывает её по-своему.
4. **Демо-режим (`?demo`) обязан вести себя так же**, как живая база: те же правила, те же
   формулы.

## 4. Процессы

### 4.1. Посещение → события **[есть, доработать]**

1. `track.js` создаёт случайный `sid`, читает UTM и домен источника, копит события.
2. `cms.js` вызывает `public_site()`; если база ответила — включает отправку.
3. События уходят пачками до 30 штук в `track()`; имена — из белого списка.

Доработать:
- **Лимит на `track`.** Сейчас его нет: проверено, аноним 20 вызовами записал 600
  поддельных посещений с чужой меткой кампании — так можно испортить воронку и ROMI. Нужно:
  не больше 200 событий на один `sid`, общий потолок событий в минуту, отбрасывание
  `utm_*` длиннее 100 символов (уже есть) и `sid` не из `[a-z0-9]{8,40}`.
- **Хранение.** Таблица растёт без ограничений. Раз в сутки `pg_cron` сворачивает день в
  `events_daily` (дата, имя, источник, кампания, тур, устройство, язык, счётчики), сырые
  события старше 13 месяцев удаляются. `stats_traffic` для старых периодов читает свёртку.

### 4.2. Заявка с сайта **[есть, доработать]**

1. Форма → `submit_lead(p)`: ловушка для ботов, проверка имени и телефона, склейка дубля
   по номеру за 3 минуты, общий лимит 40 заявок за 10 минут.
2. Вставка в `leads` со статусом `new`, UTM, языком, устройством, промокодом, `user_id`
   (если человек вошёл). Запись «создана с сайта» в историю. Событие `lead_submit`.
3. Realtime → панель: звук, уведомление, счётчик.
4. **Письмо на почту агентства [новое]:** Database Webhook на вставку в `leads` → Edge
   Function `lead-mail` → письмо на адрес из «Контакты и реквизиты»: имя, телефон, тур,
   сообщение, промокод, ссылки «Написать в WhatsApp» и «Открыть в панели». Заявки,
   внесённые вручную, писем не шлют. Результат отправки пишется в `notify_log`, неудачные
   повторяются раз в 5 минут, не больше 5 попыток.
5. **Кнопка «Продолжить в WhatsApp» [новое]:** после успешной отправки сайт показывает
   «Заявка принята» и кнопку с готовым текстом (имя, тур, сообщение). Нажатие — событие
   `wa_click` с меткой `after_form`, чтобы не путать с обычными кликами.
6. Нет связи с базой → форма сразу открывает WhatsApp с тем же текстом.

Доработать:
- Общий лимит блокирует форму всем: 40 поддельных заявок выключают приём на 10 минут.
  Добавить лимит на отправителя (хеш IP из заголовка запроса с суточной солью, сам IP не
  хранится): 5 заявок за 10 минут. Общий потолок оставить как последний рубеж.
- Промокод в заявке сейчас — любой текст. Сервер сверяет его с `coupons` и пишет в
  `details.coupon_valid` (да / нет / истёк), панель показывает это в карточке.
- `source = 'promo'` принимается функцией, но панель должна знать его название.

### 4.3. Работа с заявкой **[есть, доработать]**

Статусы и переходы:

```
new ──► contacted ──► quoted ──► won
 │          │            │        │
 └──────────┴────────────┴──► lost ◄┘ (переоткрытие / возврат)
 └──► spam
```

Любой переход разрешён (менеджер может вернуть заявку назад), но сервер при каждом:

| Событие | Что делает база |
|---|---|
| уход из `new` или первая запись звонка / WhatsApp / заметки | ставит `first_response_at`, один раз |
| вход в `won`, `lost`, `spam` | ставит `closed_at`: присланную дату, если она не в будущем, иначе `now()` |
| выход из закрытого статуса | очищает `closed_at` |
| смена статуса, ответственного | пишет в историю, кто и что |
| вход в `lost` | требует `lost_reason` |
| заявка создана вручную (`phone`, `walk_in`, `instagram`, `manual`) | ставит `first_response_at = created_at`, статус не ниже `contacted` |

Сейчас последние две строки и «присланная дата» делает только интерфейс; дату продажи он
ставит вторым запросом поверх триггера. Перенести в триггер `BEFORE INSERT OR UPDATE`.

### 4.4. Продажа **[доработать — главный блок]**

Сайт не принимает оплату; продажу вносит менеджер. Правила, которые обязана держать база:

1. `status = 'won'` ⇒ `value > 0`.
2. `profit` пустой или `0 ≤ profit ≤ value`.
3. `closed_at` (дата продажи) не в будущем.
4. `currency` = валюта из «Контакты и реквизиты», ставит сервер.
5. Любое изменение `value`, `profit`, `closed_at` у закрытой заявки пишется в историю:
   кто, было → стало (новый вид записи `money`).
6. Удаление заявки (только владелец) попадает в `audit_log`.

Сейчас ни одно из правил 1–5 база не проверяет. Проверено: запросом в обход панели
создаётся продажа без суммы, с доходом 5000 и датой через месяц; правка суммы уже
закрытой продажи не оставляет следа.

Реализация: триггер-сторож на `leads`. Проверки срабатывают, когда меняется статус или
денежные поля, — старые продажи без суммы не блокируются и остаются в срезе «Продажи без
дохода агентства».

**Возврат / отмена после продажи** (решено): менеджер переводит продажу в «Отказ» с
причиной «Возврат». Продажа уходит из выручки того дня, которым была записана, промокод
освобождается, в истории остаётся запись, кто и когда вернул. Сумма и доход в строке
сохраняются (для справки), в отчёты не попадают. «Возврат» добавить в список причин отказа.

### 4.5. Промокод **[доработать]**

- Посетитель: `check_coupon(code)` → действует ли и какая скидка. Список кодов не отдаётся.
- Код «использован», когда заявка с ним стала продажей; при переоткрытии счётчик
  уменьшается.
- Ошибка: счётчик меняется только в `AFTER UPDATE`. Проверено: продажа, внесённая сразу
  одной формой («клиент пришёл и купил») с промокодом, счётчик не увеличивает. То же при
  удалении проданной заявки и при смене кода у проданной. Нужен один триггер на
  `INSERT / UPDATE / DELETE`, который пересчитывает
  `used_count = число проданных заявок с этим кодом`.
- Колонку «В заявках» маркетолог сейчас не видит (нет доступа к `leads`). Отдавать числа
  через `stats_coupons()`: код, заявок, продаж — без имён и телефонов.

### 4.6. Кампания → ROMI **[есть, доработать]**

1. Маркетолог создаёт кампанию: `utm_campaign` уникален, расход вводится руками.
2. Ссылка с метками → сайт кладёт метки в события и в заявку.
3. `stats_traffic` отдаёт по каждой метке: посещения, контакты, заявки, продажи, выручку,
   доход (введённый) и выручку без дохода (для оценки по марже).
4. ROMI = (доход − расход) ÷ расход.

Доработать:
- Расход и выручка должны быть в одной валюте. Сервер ставит `campaigns.currency` сам; при
  смене валюты панели старые суммы не пересчитываются — показывать предупреждение.
- Маржу для оценки сейчас подставляет интерфейс (и берёт 12 %, если не задана). Оценку
  считать в SQL и отдавать готовое поле `profit_total` с флагом `estimated`.
- Расход — одно число за всю жизнь кампании, поэтому ROMI «за период» посчитать нельзя.
  Достаточно ли этого — вопрос №5.

### 4.9. Аккаунт клиента и кабинет **[доработать]**

- Регистрация → триггер создаёт `profiles` (роль `client`, согласие только явное).
- **Подтверждение почты [новое].** Вход через Google и Mail.ru подтверждения не требует —
  адрес уже проверен ими. Регистрация по почте с паролем: Supabase Auth → «Confirm email»
  включено. В одном письме — ссылка и код из 6 цифр: можно нажать ссылку или ввести код в
  форме на сайте (удобно, когда почта открыта на другом устройстве). До подтверждения войти
  нельзя; повторная отправка — не чаще раза в минуту. Письма идут через свой
  почтовый сервис (SMTP), встроенная отправка Supabase рассчитана на единицы писем в час.
  В списки подписчиков и в `audience_list()` попадают только подтверждённые адреса.
  Заявку с формы можно отправить без входа и без подтверждения — как сейчас.
- **Дата рождения [новое].** Поле `profiles.birth_date` (дата, без времени),
  обязательное. При регистрации по почте — в форме; вошедшие через Google / Mail.ru
  заполняют на экране первого входа рядом с согласием на рассылку, и без неё кабинет не
  открывается. Изменить можно в кабинете. Сервер проверяет: не в будущем, возраст от 16 до
  120 лет. Назначение — поздравление со скидкой.
  Панель: дата в карточке клиента («Клиенты и команда») и раздел маркетолога «Именинники
  месяца» с выгрузкой CSV — RPC `birthdays(month)`, только клиенты с согласием на рассылку
  и подтверждённой почтой. Доступ: владелец и маркетолог; `users_list()` для менеджера
  дату не отдаёт. В тексте политики конфиденциальности на сайте дописать, зачем собирается
  дата рождения.
- Согласие на рассылку: дата и источник хранятся; выгрузка — `audience_list()`.
- **Разрыв:** кабинет читает таблицу `bookings` и обещает «отправьте заявку — она появится
  здесь», но заявки пишутся в `leads`, которые клиенту не видны. Проверено: клиент после
  отправки видит 0 строк. `bookings` никто не заполняет, раздел панели убран, поэтому
  счётчик «бронирований» в `users_list` и `audience_list` всегда 0.
- Решение: RPC `my_requests()` — свои заявки по `user_id`: дата, тур, статус в словах для
  клиента («получили», «на связи», «предложение отправлено», «оформлено», «закрыто»); без
  суммы, дохода, заметок. Кабинет читает его. В `users_list` / `audience_list` счётчик
  заменить на «заявок / покупок». Таблицы `bookings` и `coupon_redemptions` заморозить
  (снять права на запись), удалить после запуска.

## 5. Словарь метрик

Все даты и сутки — по Еревану (`Asia/Yerevan`). Спам не участвует нигде.

| Метрика | Формула | По какой дате | Где |
|---|---|---|---|
| Посещение | событие `page_view` (= одна загрузка страницы) | `events.ts` | трафик, сводка |
| Контакт | `wa_click` + `tel_click` | `events.ts` | трафик |
| Заявка | строка `leads`, статус ≠ `spam` | `created_at` | везде |
| Продажа | заявка в `won` с `value > 0` | `closed_at` | сводка, менеджеры |
| Выручка периода | Σ `value` продаж | `closed_at` | сводка владельца |
| Доход агентства | Σ `profit`; где пусто — `value × маржа`, с пометкой ≈ | `closed_at` | сводка, ROMI |
| Средний чек | выручка ÷ число продаж | `closed_at` | сводка |
| Конверсия в продажу | продажи ÷ (продажи + отказы), закрытые в периоде | `closed_at` | сводка, менеджеры |
| Посещения → заявка | заявки ÷ посещения | `created_at` / `ts` | сводка, трафик |
| Первый ответ | медиана (`first_response_at − created_at`), только заявки с сайта | `created_at` | сводка, менеджеры |
| В норматив | доля заявок с сайта с ответом ≤ `hours.sla_min` | `created_at` | сводка |
| Прогноз | Σ `value` в `quoted` × конверсия периода | сейчас | сводка |
| Выручка канала / кампании | Σ `value` продаж среди заявок, **пришедших** в периоде | `created_at` (когорта) | трафик, кампании |
| CPL / CPA | расход ÷ заявки / продажи кампании | вся жизнь кампании | кампании |
| ROMI | (доход − расход) ÷ расход | вся жизнь кампании | кампании |
| CTR промо | клики ÷ показы | `events.ts` | промо |

Что закрепить:

1. **Две выручки — это нормально, но подписывать.** У владельца — «по дате продажи»
   (сколько заработали в октябре). У маркетолога — «по заявкам периода» (сколько принесли
   октябрьские обращения). Цифры не обязаны совпадать; в панели каждая подписана.
2. **Канал заявки определяет одна SQL-функция** `lead_channel()`, её используют и сводка, и
   трафик, и кампании. Порядок: ручной источник (звонок, визит, Instagram Direct,
   WhatsApp) → `utm_source` → домен перехода (свой домен = прямой заход) → прямой заход.
   Сейчас сводка и `stats_traffic` считают по-разному: проверено, звонки и визиты в офис
   попадают маркетологу в «Прямые заходы» и завышают их конверсию.
3. **Первый ответ считается в рабочих часах.** Заявка в 23:00 с ответом в 10:05 — это
   5 минут при открытии в 10:00. Считает SQL-функция по `site_settings.hours`.4. **Валюта одна** (`company.currency`). Цена «от» в карточке тура — отдельное поле для
   сайта, в отчётах не участвует.

## 6. Контракт API

Сайт:

| Вызов | Статус | Что делает |
|---|---|---|
| `public_site()` | есть | весь контент одним ответом |
| `submit_lead(p)` | доработать | + лимит на отправителя, проверка промокода |
| `track(events)` | доработать | + лимиты |
| `check_coupon(code)` | есть | действует ли код |
| `my_requests()` | новое | заявки вошедшего клиента |

Панель:

| Вызов | Статус | Что делает |
|---|---|---|
| `whoami()` | есть | роль и имя |
| таблица `leads` (чтение, вставка, правка) | доработать | правила §4.3–4.4 в триггере; чтение — страницами |
| `stats_sales(from, to)` | новое | KPI сводки, по дням, по менеджерам, причины отказов, каналы — всё из §5 |
| `stats_traffic(from, to)` | доработать | `lead_channel()`, готовый `profit_total`, чтение свёртки |
| `stats_coupons()` | новое | заявки и продажи по коду, без PII |
| `birthdays(month)` | новое | именинники месяца: имя, почта, дата, язык — владельцу и маркетологу |
| `users_list()`, `audience_list()` | доработать | счётчик заявок вместо бронирований |
| `set_role(user, role)` | доработать | защита последнего владельца |
| контентные таблицы, `site_settings`, `audit_log`, Storage `media` | есть | |

**Почему нужен `stats_sales`.** Сейчас сводка скачивает заявки в браузер и считает сама.
Запрос просит 3000 строк, но Supabase по умолчанию отдаёт не больше 1000 за запрос
(API → Max rows). После тысячной заявки выручка, конверсия и рейтинг менеджеров начнут
молча терять старые записи. Целевое состояние: цифры считает SQL, а список заявок
грузится так: все открытые + закрытые за выбранный период, остальное — по поиску и
страницами.

## 8. Эксплуатация

| Тема | Требование |
|---|---|
| Миграции | Вместо двух файлов «вставить в SQL Editor» — папка `supabase/migrations/` с номерами, накат через Supabase CLI. Изменения из §7 — отдельными миграциями, повторный запуск безопасен |
| Стенд | Второй проект Supabase для проверки миграций; боевой ключ в `supabase-config.js` не меняется |
| Регион | Проект в Сиднее (~300 мс до Армении). Переезд во Франкфурт — по плану §8.1 |
| Резервные копии | На бесплатном тарифе их нет. Либо тариф Pro (ежедневные копии), либо еженедельный `pg_dump` по расписанию в приватное хранилище |
| Вход в панель | Почта и пароль, минимальная длина пароля 10. Двухфакторного входа нет (решение заказчика); готовая реализация лежит в истории, коммит `cf7067b` |
| Секреты | `service_role`, ключи Mail.ru и почтового сервиса — только в секретах Edge Functions |
| Наблюдение | «Готовность сайта» показывает: версию схемы, время последнего события, последней заявки |
| Скорость | `public_site()` ≤ 300 мс, `stats_*` за 90 дней ≤ 1 с при 10 000 заявок и 1 млн событий. Индексы: `leads(closed_at)`, `leads(assigned_to)`, `leads(user_id)`, `events(utm_campaign, ts)` |
| Нагрузка | До 100 заявок в день ≈ 36 000 в год, события — миллионы строк в год. Поэтому расчёт цифр в SQL (`stats_sales`), загрузка заявок страницами и свёртка событий — обязательные пункты, а не «на вырост». Общий лимит `submit_lead` поднять с 40 до 60 заявок за 10 минут |
| Демо | `DemoApi` реализует те же правила §4 и формулы §5; расхождение = ошибка |

### 8.1. Переезд: куда и как

**Куда.** Остаёмся на Supabase, меняем только регион: новый проект во Франкфурте
(`eu-central-1`). Регион у существующего проекта поменять нельзя, поэтому это новый проект
и перенос. Уходить с Supabase на свой сервер не нужно: вход, права по строкам, функции,
хранилище фото и живые уведомления — это весь наш бэкенд, и на другой платформе его
пришлось бы писать заново (отдельный API, авторизация, хостинг, обновления), не получив
ничего взамен. SQL при этом обычный Postgres — если когда-нибудь понадобится, базу можно
унести целиком.

**Когда.** Первым шагом, до работ из §7. Старую базу решено не переносить, поэтому шаги
2–3 сводятся к запуску миграций на чистом проекте; контент и фото менеджер вносит через
панель уже в новый проект.

**Порядок.**

1. *Новый проект.* Supabase → New project → Frankfurt. Записать URL, publishable key,
   пароль базы.
2. *Схема и данные* — через Supabase CLI, тремя файлами со старого проекта:
   `supabase db dump --role-only`, `supabase db dump` (схема), `supabase db dump --data-only
   --use-copy` → накатить `psql` на новый. В выгрузку входят `auth.users` с хешами
   паролей: аккаунты и пароли сохраняются, людям нужно только войти заново.
   Если в старой базе нет ничего ценного (только тестовые заявки и свой аккаунт) — проще:
   выполнить `schema.sql` + `admin.sql` на новом проекте, зарегистрироваться и назначить
   владельца, как в `SETUP-ADMIN.md`.
3. *Фото.* Файлы бакета `media` выгрузка не переносит: скопировать скриптом (скачать из
   старого, загрузить в новый с теми же путями), затем заменить адрес старого проекта в
   `tours.photo_url`, `reviews.photo_url`, `team.photo_url` одним `update`.
4. *Вход.* Authentication → URL Configuration: Site URL и Redirect URLs как в старом.
   Google: в Google Cloud добавить новый адрес
   `https://<новый-ref>.supabase.co/auth/v1/callback`, ключи вставить в новый проект.
   Mail.ru: в приложении Mail.ru поменять Redirect URI на новый адрес функции.
   Шаблоны писем и SMTP — перенести руками.
5. *Функции.* `supabase functions deploy mailru-auth` в новый проект; `lead-notify` не
   переносится, папка удаляется из репозитория; вместо неё — `lead-mail`. Секреты завести заново (
   `MAILRU_*`, `SB_URL`, `SB_SERVICE_ROLE_KEY`, `SITE_URL`). Database Webhook на вставку
   в `leads` создать заново.
6. *Сайт.* Единственное место в коде — `js/supabase-config.js` (URL и ключ). CSP в
   страницах разрешает `*.supabase.co`, её менять не нужно. Поднять номер версии в
   ссылках на скрипты, чтобы браузеры не держали старый конфиг. Обновить `SETUP-AUTH.md`.
7. *Проверка на новом проекте до переключения:* `rls.test.mjs`, вход по почте, Google и
   Mail.ru, заявка с формы → панель, загрузка фото, сценарий из §9.
8. *Переключение.* Вечером: шаг 2 повторить начисто (свежие данные) → `git push` с новым
   конфигом → проверить заявку на боевом домене. Заявки, отправленные в эти минуты, не
   теряются: форма при недоступной базе открывает WhatsApp.
9. *После.* Старый проект поставить на паузу, удалить через две недели. Ключи старого
   проекта нигде не остаются.

**Тариф.** На бесплатном нет резервных копий, а проект без обращений неделю засыпает.
Для боевой базы с клиентами — Pro (25 $/мес., ежедневные копии). Если пока бесплатный —
еженедельный `supabase db dump` по расписанию в приватное хранилище.

## 9. Приёмка

Бэкенд принят, когда:

1. Все проверки `rls.test.mjs` зелёные, включая новые: менеджер не меняет роли; продажа
   без суммы, с доходом больше суммы и с датой в будущем отклоняется; промокод считается
   при любой форме продажи; клиент видит свои заявки и не видит чужих; маркетолог не
   получает телефоны ни одним вызовом; 201-е событие одного `sid` отбрасывается.
2. Сквозной сценарий на стенде: заход по UTM-ссылке → заявка с промокодом →
   панель → «На связи» → «Предложение» → «Продажа» вчерашней датой. После этого:
   выручка и доход появились во вчерашнем дне сводки; у кампании +1 заявка, +1 продажа,
   ROMI пересчитан; у промокода «использован 1»; в истории заявки видно, кто и когда;
   у менеджера +1 продажа; в кабинете клиента статус «оформлено».
3. Те же цифры в сводке, в CSV-выгрузке заявок и в прямом SQL-запросе совпадают.
4. При 1500 заявках в базе сводка за «всё время» сходится с SQL.
5. Переоткрытие продажи убирает её из выручки, возвращает промокод и оставляет запись в
   истории.
